# Security

This document describes the security controls implemented in CDN Network and identifies known limitations and recommended improvements.

---

## Authentication

### API Key Format and Storage

API keys are generated by `internal/domain/apikey/apikey.go`:

- Keys are 46 characters long with the format `ak_<base64url(32 random bytes)>`.
- The random bytes are generated via `crypto/rand` (cryptographically secure PRNG).
- Only the first 12 characters (`KeyPrefix`) and the SHA-256 hash of the full key are stored in PostgreSQL.
- The plaintext key is returned **once** at creation time and is never stored, logged, or retrievable.

Authentication flow (`internal/middleware/middleware.go`):
1. Extract `Authorization: Bearer <token>` header.
2. Verify token starts with `ak_`.
3. Hash the token with SHA-256.
4. Look up the hash in `api_keys.key_hash`.
5. Verify the key is active (not revoked, not expired).
6. Store the `apiKeyID` UUID in Fiber locals.
7. Fire-and-forget: update `last_used_at` in a separate goroutine.

### Key Expiry and Revocation

- Keys may have an optional `expires_at` timestamp.
- `IsActive()` returns false if `status == "revoked"` OR `revoked_at != nil` OR `IsExpired()`.
- Revoked keys cannot be re-activated.

## Input Validation

All handler inputs are validated at two layers:

1. **`go-playground/validator`** — struct-tag validation (min/max length, enum values, format).
2. **Domain constructors** (`bucket.NewBucket`, `file.NewFile`, `cdn.NewDomain`, etc.) — business rule validation that returns typed sentinel errors.

UUID path parameters are parsed with `uuid.Parse`; invalid values return 400 before the use case is called.

---

## Rate Limiting

Rate limiting is applied per client IP address using a Redis-backed fixed-window counter with a penalty box. The limiter is in `internal/security/ratelimit`.

| Kind | Window | Max requests | Penalty box |
|---|---|---|---|
| API (`/api/v1/*`) | 1 second | 10 req | After 5 violations: 5-minute block |
| Delivery (`/cdn/*`) | 1 second | 25 req | After 5 violations: 5-minute block |
| Upload | 1 second | 5 req | After 5 violations: 5-minute block |

Rate limit counters are **IP-based**. Clients behind NAT or shared proxies share the same bucket.

If Redis is unavailable, rate-limit checks **fail open** (requests are allowed). This is documented behaviour to prevent a Redis outage from taking down the API.

## Trusted Proxy Configuration

`X-Forwarded-For` and `X-Forwarded-Host` headers are only honoured when:
1. `TRUSTED_PROXIES` is set to one or more CIDR ranges.
2. The connecting IP falls within a trusted range.

Without `TRUSTED_PROXIES`, Fiber uses the direct peer address. This prevents clients from spoofing their IP address to bypass rate limiting.

When using Nginx (the provided example in `deploy/nginx/`), configure `TRUSTED_PROXIES` to the Docker network's CIDR (e.g. `172.20.0.0/16`).

## Object Key Security

Object keys are generated server-side and cannot be influenced by clients in a meaningful way. The `objectKey` function in `internal/usecase/file_usecase.go`:

- Discards any directory component from the original filename (`filepath.Base`).
- Strips `..`, `.`, and path separators.
- Allows only `[a-z0-9\-_.]` — all other characters become hyphens.
- Prepends a UUID to guarantee uniqueness and unpredictability.
- Prefixes with `YYYY/MM/` for date partitioning.

This prevents path traversal attacks when the object key is used as a filesystem path.

## Presigned URL Security

Presigned URLs for private file access use HMAC-SHA256:

```
signature = HMAC-SHA256(STORAGE_SIGNING_SECRET, METHOD + bucket + key + expires_unix)
```

- Expiry is embedded in the URL and enforced server-side.
- If `STORAGE_SIGNING_SECRET` is empty, presigning still works but with an empty key — **configure a strong secret in production**.
- Presigned PUT URLs expire in 15 minutes; presigned GET URLs expire in 15 minutes.
- Maximum presigned PUT body size: 5 GiB (enforced by the storage HTTP handler).

## HTTP Security Headers

Applied to every response by middleware in `main.go`:

| Header | Value |
|---|---|
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `X-Permitted-Cross-Domain-Policies` | `none` |

`Content-Security-Policy` and `Strict-Transport-Security` are **not** set by the application. If required, add them at the reverse proxy (see `deploy/nginx/nginx.conf`).

---

## Error Response Security

- **5xx errors** never expose internal error messages. The response body always contains `{"code":"INTERNAL_ERROR","message":"an unexpected error occurred"}`.
- **4xx errors** expose the application-level error message but not stack traces or database details.
- Panics are caught by the `recover` middleware and logged server-side only; the client receives a 500 with no detail.

---

## CORS

CORS is configured via `CORS_ALLOWED_ORIGINS`. `AllowCredentials` is enabled automatically when the origin list is a non-wildcard explicit list. Wildcard origins (`*`) are accepted as a value but will disable `AllowCredentials` automatically.

In production, `CORS_ALLOWED_ORIGINS` should be set to the exact origins of your frontend application.

---

## Secret Handling

- `POSTGRES_PASSWORD`, `REDIS_PASSWORD`, and `STORAGE_SIGNING_SECRET` are read from the environment and never logged.
- The database connection URL is assembled in memory and not exposed in logs or responses.
- The `logs/app.log` file does not contain credential values (verified by inspection of the logger and middleware).

## Known Limitations

1. **No DNS verification for CDN domains** — `POST /cdn-domains/:id/verify` marks a domain active without any DNS challenge. Any user can claim any hostname.

2. **No scope enforcement** — API keys store a `scopes` array but no endpoint checks scopes. Every active key has full access to all endpoints.

3. **No per-key resource isolation** — a key can theoretically access any bucket or file by UUID. The `ListBuckets` endpoint filters by `api_key_id`, but `GetBucket` and all file/CDN endpoints do not verify ownership.

4. **`fmt.Println` in delivery handler** — `CDNDeliveryHandler.Serve` logs the object key to stdout unconditionally. Remove before production deployment.

5. **No audit log** — API key usage is tracked (`last_used_at`) but individual API calls are not recorded in an audit trail.

6. **SMTP not wired** — email-based security flows (e.g. key rotation notifications) are not implemented.

7. **Fraud detection is a stub** — `internal/security/fraud` contains only a package declaration.

8. **JWT_SECRET is loaded but unused** — if JWT authentication is added in the future, ensure the secret is at least 32 characters.

9. **No TLS termination** — the application listens on plain HTTP. TLS must be handled by a reverse proxy.

---

## Recommended Improvements

- Implement scope checking in middleware before handlers.
- Add ownership verification to `GetBucket`, `GetFile`, and CDN endpoints.
- Implement DNS TXT record verification for CDN domain registration.
- Add a `Content-Security-Policy` header at the reverse proxy.
- Add `Strict-Transport-Security` at the reverse proxy once TLS is configured.
- Remove the `fmt.Println(objectKey)` debug statement.
- Add rate limiting to the presigned URL PUT endpoint.
- Rotate `STORAGE_SIGNING_SECRET` — sign new URLs with the new secret while accepting the old secret for a transition window.
- Consider adding request-level audit logging to a separate log stream.
